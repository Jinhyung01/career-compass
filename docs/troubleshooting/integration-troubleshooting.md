# Career Compass 트러블슈팅

## 1. 브랜치 병합 과정의 도메인 변경 충돌

기업 검색 기능을 개발하는 동안 `main` 브랜치에는 실제 JWT 인증과 분석 리포트 기능이 추가되어 동일한 테스트·설정 파일에서 충돌이 발생했다. 한쪽 변경을 단순 채택하면 기업 API 또는 인증·분석 흐름이 유실될 수 있어, 충돌 파일의 호출 관계와 테스트 의도를 비교한 뒤 두 도메인의 변경 사항을 함께 유지하도록 병합했다. 이후 전체 테스트로 기존 기능의 회귀 여부를 확인했다.

## 2. DB 스키마와 API 응답 간 불일치

기업별 현직자 수와 인사이트 수를 제공하기 위해 DB에는 `people`, `insight` 컬럼을 추가했지만, 엔티티와 DTO만 변경해서는 실제 API 응답에 값이 나타나지 않았다. 스키마, JPA 엔티티, 응답 DTO, 서비스 매핑을 하나의 데이터 흐름으로 추적하여 누락된 매핑을 보완했고, 기업 목록과 상세 조회에서 기존 응답 구조를 유지하면서 통계가 함께 반환되도록 정리했다.

## 3. 대량 목업 데이터의 참조 정합성 문제

기업 데이터를 120개로 확장하는 과정에서 기존 인사이트 데이터가 참조하는 기업 코드와 새 기업 데이터의 코드가 일치해야 했다. 단순히 회사명만 교체하면 외래 키 관계와 분석 결과가 어긋날 수 있어, `company_code`를 안정적인 식별자로 유지하고 기업명·산업·통계 데이터를 그 코드에 맞춰 갱신했다. 이를 통해 기업 조회와 분석 데이터가 동일한 기업을 참조하도록 만들었다.

## 4. 인증 실패 응답의 일관성 확보

보호된 API에서 인증 정보가 없거나 유효하지 않을 때 요청이 컨트롤러에 도달하기 전에 Spring Security 필터에서 차단되므로, 일반 예외 처리만으로는 프로젝트의 오류 응답 형식을 유지할 수 없었다. 인증 진입점과 접근 거부 처리기를 별도로 구성해 `401`과 `403`에서도 `{ code, message }` 형식의 JSON을 반환하도록 통일했다. Postman으로 정상 인증, 잘못된 인증, 존재하지 않는 리소스 조회를 각각 검증했다.

## 5. 테스트와 구현 간 계약 변경 대응

기업 응답 필드와 서비스 생성자 의존성이 변경되면서 기존 단위 테스트의 객체 생성 코드와 예상 응답이 실제 구현과 달라져 테스트가 실패했다. 실패 지점을 기준으로 테스트 데이터를 새 계약에 맞게 조정하고, 서비스와 컨트롤러 테스트를 분리해 비즈니스 매핑과 HTTP 응답을 각각 검증했다. 그 결과 필드 추가 이후에도 기존 기업 검색·상세 조회 동작이 유지되는지 확인할 수 있었다.

---

이번 트러블슈팅을 통해 개별 코드 수정뿐 아니라 **DB 스키마 → 엔티티 → 서비스 → API → 테스트**로 이어지는 전체 데이터 흐름과, 병합 시 도메인 간 영향 범위를 함께 검증하는 것이 중요하다는 점을 확인했다.
